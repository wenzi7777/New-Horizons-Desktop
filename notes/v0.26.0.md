# v0.26.0

**錄製的 App 事件改為跟著感測器串流送達，時間戳和主 CSV 使用同一套時間；不再錄進錄製開始前的事件。**

## 錄製檔的時間戳

一份錄製有兩個檔案：

- `<HHMMSS>.csv`：感測器資料。檔名和資料夾名稱是 **UTC** 時間。
- `<HHMMSS>.events.csv`：App 事件。

兩個檔案的 `timestamp_ms` 現在都是 Unix epoch 毫秒（UTC）。事件的時間就是它發生的那個 frame 在主 CSV 裡的時間，所以兩個檔案可以直接用 `timestamp_ms` 或 `frame_seq` 對齊。

主 CSV 的 `time_ref` 欄說明時間來源：

- `device`：裝置在掃描當下用已對時的時鐘蓋的時間，不含網路延遲。
- `received`：裝置還沒對時，改用後端收到封包的時間，會包含網路延遲。

events CSV 在最後新增兩欄（原有欄位的順序不變）：

- `uptime_ms`：裝置開機後的毫秒數。以前的 `timestamp_ms` 就是這個值。
- `time_ref`：
  - `device` 或 `received`：和該 frame 在主 CSV 的那一列相同。
  - `estimated`：那個 frame 在傳輸中遺失，時間由前後的 frame 推算；遺失標記列也是這個值。
  - `uptime`：沒有對應的錄製，只能用開機時間。

## 事件改為跟著串流送達

- 搭配韌體 v1.16.0 以上，事件會放在感測器封包裡送出，延遲只有一兩個 frame，錄製期間不再每 0.5 秒送一次 `app_events` 指令。經 Hub 時，指令通道不會再被這些查詢佔用。
- 封包遺失時，後端從事件序號的缺口發現，立刻向裝置要回缺少的事件。裝置的緩衝區（32 筆）裡已經沒有的，會在 events CSV 寫一列 `events_dropped`，並註明數量。
- 補回的事件可能寫在較晚的位置，需要時請依 `seq` 或 `frame_seq` 排序。
- 舊韌體照舊每 0.5 秒查詢一次，時間戳一樣會換算成主 CSV 的時間。
- 不知道裝置的矩陣大小時（例如後端剛重開），帶事件的封包以前會被丟棄，現在可以自行推算。

## 錄製開始前的事件

開始錄製後的第一次查詢會拿到裝置開機以來的所有事件，以前全部會寫進 events CSV。現在只保留錄製期間的事件。

## 修正舊的錄製

用 `scripts/fix_event_timestamps.py` 可以把舊的 events CSV 改成新格式：時間換算成主 CSV 的時間，並刪掉錄製開始前的事件。原檔會先備份成 `.events.csv.bak`。

```bash
python3 scripts/fix_event_timestamps.py <錄製的 .csv 路徑> [...]
```

加 `--dry-run` 只顯示結果，不修改檔案。
